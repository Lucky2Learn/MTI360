# ADR-0013 — Audit Events: One Append-Only Table, In-Transaction and Post-Request Writers

- **Status:** Accepted (T01-02 locked decisions 1.1–1.9; refines T01-00 decision D22)
- **Date:** 2026-10-01
- **Task:** T01-02
- **Related:** [ADR-0004](0004-tenant-isolation.md), [ADR-0005](0005-identity-and-session-realms.md), [backend-foundation.md](../architecture/backend-foundation.md) §3 and §12, [security.md](../architecture/security.md) §11, [tenancy.md](../architecture/tenancy.md) §6

## Context

CLAUDE.md §51 and security.md §11 require audit records for authentication, authorization changes, support sessions, tenant, financial and compliance changes, AI actions and data access. Decision D22 (T01-00) splits them into two kinds:

- **Audit events** are part of the change they describe. They must commit or roll back with it.
- **Security events** (a failed sign-in, a denied request) usually come from requests that fail and roll back. They must still be stored.

T01-02 runs before tenancy (T01-03) and identity (T01-04, T01-06). No `tenants`, `users` or `platform_users` table exists yet, and nothing in the repository produces audit events yet.

## Decision

### 1. One mixed-scope, append-only table

- There is exactly one table, `audit_events`, for every category. There is no `security_events` table.
- The table is **mixed-scope**:
  - `tenant_id` holds the tenant of a tenant-scoped event;
  - `tenant_id` is `NULL` for platform, system and pre-authentication events.
- The code lives in `backend/app/core/audit/`. The post-request flush integrates with the request infrastructure, and `core` must never import `modules` (import-linter layers).

### 2. Schema

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` PK | UUIDv7 generated by the application (`app.core.ids.new_id`) |
| `created_at` | `timestamptz` | `now()` set by the database; the `TimestampMixin` column without `updated_at` |
| `request_id` | `uuid` | From `RequestContext`; correlates with the request log. Not renamed to `correlation_id` |
| `realm` | `varchar(16)` | The `Realm` vocabulary (`platform`, `tenant`, `student`, `public`, `webhook`, `system`), checked |
| `tenant_id` | `uuid` NULL | **No foreign key** (§3) |
| `principal_id` | `uuid` NULL | `RequestContext.principal_id`. The realm identifies which identity table it refers to (ADR-0005). No foreign key |
| `category` | `varchar(16)` | Exactly `security`, `admin`, `data_access` or `domain`, checked |
| `event_type` | `varchar(100)` | Dotted lower-case name (`auth.login_failed`), checked |
| `target_type`, `target_id` | `varchar(64)`, `uuid` NULL | Generic resource reference: no foreign key and no polymorphic relationship. An ID requires a type |
| `metadata` | `jsonb` | A JSON object, at most 8 KiB in the database (backstop for the 4 KiB application limit) |

- **Indexes**, each with an access pattern:
  - `(tenant_id, created_at)` for the tenant audit read (T01-08);
  - `(category, created_at)` for the platform audit and security-event views (T01-07);
  - `(request_id)` for correlation with the request log.
- **Not stored:**
  - `support_session_id`, campus, IP address, user agent, a result field and a risk level;
  - none of these has a trusted source yet (support sessions are Phase 02; there is no trusted proxy chain);
  - each will be added by the task that introduces its source.
  - The result is part of the event type (`auth.login_failed`). See INC-35.

### 3. Deliberate exceptions

1. **`tenant_id` has no foreign key.** `tenants` arrives in T01-03, and audit history must stay durable independently of the lifecycle of tenant records. No placeholder tenants table exists.
2. **Not `TenantScopedMixin` and no composite foreign keys.** The table is mixed-scope, and its own Row-Level Security policies protect it (§4).
3. **No foreign keys to identity or business tables.** Those tables belong to later tasks and to modules that `core` may not know about.

### 4. Database enforcement

- **Privileges.** The default privileges from `database/init/01-roles.sh` would give `mti_app` full DML and `mti_readonly` SELECT on every new table. Migration `0002` replaces them:
  - `mti_app`: `SELECT`, `INSERT` only;
  - `mti_readonly`: no access in T01-02. A governed Data Agent may receive scoped audit access in a later task.
  - The owner (`mti_owner`) runs migrations only. `mti_app` is not the owner and stays `NOBYPASSRLS`.
- **Append-only, twice.**
  - `mti_app` has no UPDATE, DELETE or TRUNCATE privilege.
  - The triggers `audit_events_reject_update_delete` (row level) and `audit_events_reject_truncate` (statement level) reject those operations for **every** role, including the owner.
  - A future retention task needs an explicit, reviewed migration path for deletion.
- **Row-Level Security: the first policies in the repository.**
  - The policies read the transaction-local context from `app.core.db.settings` (`SET LOCAL`, T01-01).
  - An unset setting reads as NULL: `nullif(current_setting('app.tenant_id', true), '')::uuid`.

  | Policy | Command | Rule |
  |---|---|---|
  | `audit_events_platform_read` | SELECT | `app.realm = 'platform'`: every row, including `NULL`-tenant events |
  | `audit_events_tenant_read` | SELECT | `app.realm = 'tenant'` and `tenant_id = app.tenant_id`: the tenant's own rows only, never `NULL`-tenant rows |
  | `audit_events_insert` | INSERT | `tenant_id IS NOT DISTINCT FROM app.tenant_id` and `realm = app.realm` |

  - The student, public, webhook and system realms have **no read policy**, so they see nothing.
  - The system realm may insert `NULL`-tenant events, but it has no audit read access.
  - RLS is enabled but not forced on the owner, which runs migrations only.
  - The insert policy also binds `realm` to the trusted realm. This goes beyond the tenant rule, so a row can never claim another realm than its context.

### 5. Writers

- **`write_audit_event(session, event_type, target=, metadata=)`** is for the `admin`, `data_access` and `domain` categories.
  - It inserts through the caller's `DbSession`, inside the request transaction, so it opens no other connection.
  - The mutation and its audit record commit or roll back together.
  - A failed audit insert fails the request: it is never reported as a success.
  - It refuses `security` events.
- **`record_security_event(event_type, target=, metadata=)`** validates and redacts the event and appends it to a request-local, in-memory buffer.
  - The buffer holds at most 32 events per request; further events are dropped and counted in the log.
  - It makes **no database access** during the request.
- **Lifecycle.**
  - The realm guard is a function-scoped dependency resolved before every other one, so it exits last. On exit it calls `flush_security_events`.
  - At that point the `DbSession` dependency has already committed or rolled back and returned its connection to the pool.
  - The flush opens a fresh, short transaction through `context_transaction`, which re-establishes the same trusted context with `SET LOCAL`, inserts the buffered events and commits.
  - Only then is the response sent. This happens on every path, including error responses and requests the guard denies.
  - A request never holds two connections, and the request lifecycle passes on a pool of one connection.
- **Inputs.**
  - Realm, tenant, principal and request ID always come from the trusted `RequestContext`, never from arguments.
  - Event types are code-declared `AuditEventType` constants bound to one category, never free strings.

### 6. Security-event flush failure policy

- If the flush fails, it logs `audit.security_flush_failed` at ERROR level. The entry contains only the request ID, realm, event count and exception class: never metadata, SQL or the exception text.
- It then swallows the failure:
  - the response the request already determined is unchanged;
  - the committed request transaction stays committed;
  - nothing is retried.
- **T01-02 has no outbox, queue, worker, retry or dead-letter mechanism.** The first background-job task may move security events to the transactional outbox (backend-foundation.md §5).

### 7. Metadata

- Metadata is a flat object with code-chosen keys (`^[a-z][a-z0-9_]*$`, at most 64 characters, at most 32 keys).
- Values are `None`, `bool`, `int`, finite `float`, `str` (truncated at 256 characters) or `UUID`, or a list of at most 16 of these.
- The serialized object is at most 4 KiB.
- **Sensitive keys are redacted, not rejected.** A key whose name matches the logging redaction pattern (password, secret, token, cookie, authorization, CSRF, session other than `*_session_id`, API key, credential, OTP) or contains JWT or prompt keeps its name, and its value becomes `[REDACTED]` before persistence.
  - Redaction is deterministic and keeps the event.
  - The rule works on key names: values under ordinary keys must never contain secrets.
- Anything else raises `AuditMetadataError` (a programming error) with a message that never contains values.

## Consequences

- A rolled-back request still leaves its security trail, without doubling connection use under load (brute force).
- A security event can be lost if the flush fails; it is logged. This is accepted until the outbox exists.
- Tenants can never read another tenant's or the platform's events, even through a bug in a repository, because RLS enforces it in the database.
- Nobody can rewrite audit history through the application role; the owner cannot do it by accident either.
- Tests cannot clean up audit rows. They identify their rows by unique request IDs and never count the table.
- T01-03 will reuse `context_transaction` for `system_context`, and T01-03 … T01-08 can use the writers as soon as they have producers.

## Alternatives considered

- **A separate `security_events` table:** two read paths, two sets of policies and duplicated columns, for no isolation benefit. Rejected (locked decision 1.3).
- **Writing security events on a second connection during the request:** this doubles the connections held per failing request, exactly when failures spike, and deadlocks a one-connection pool. Rejected (locked decision 1.1).
- **Writing security events after the response (request-scoped dependency or background task):** the order would no longer be "flush, then response", and failures would happen after the client has its answer. Rejected.
- **`BYPASSRLS` or a separate platform role for audit reads:** this weakens the single runtime-role model. The platform branch of the policy is explicit instead.
- **Rejecting sensitive metadata keys:** a producer mistake would turn into a failed request or a lost security event. Redaction keeps the event and still never stores the value.
- **Grants only, without triggers:** a later default-privilege change or manual grant would silently re-enable UPDATE and DELETE. The triggers make append-only independent of grants.
