# Backend Foundation (T01-01)

- **Status:** Implemented in T01-01. Authentication, tenancy, RBAC and audit build on it in T01-02 … T01-10.
- **Decisions:** T01-00 decisions D1–D22 (§10), [ADR-0001](../adr/0001-stack.md), [ADR-0004](../adr/0004-tenant-isolation.md)–[ADR-0006](../adr/0006-api-prefixes.md), [ADR-0010](../adr/0010-sessions-credentials-and-csrf.md)–[ADR-0012](../adr/0012-application-level-encryption.md)
- **Related:** [repository-structure.md](repository-structure.md) §3, [tenancy.md](tenancy.md), [security.md](security.md), [ci.md](ci.md), [runbook](../runbooks/local-development.md)

This is the engineering contract for every backend module: where code lives, how a request reaches the database, how errors, logs and pages look, and how it is tested. **No business tables and no authentication exist yet.** Every authenticated realm denies every request (§6).

## 1. Layout and boundaries

```text
backend/app/
  main.py           create_app(): settings → logging → engine → handlers → middleware → realms
  api/              realm routers and guards (realms.py) + one module per realm
  core/             infrastructure only; imports no module
    config.py ids.py context.py errors.py logging.py middleware.py schemas.py pagination.py
    db/             base.py (Base, mixins) engine.py settings.py (SET LOCAL) session.py (DbSession)
  modules/          business domains (from T01-02)
backend/migrations/ Alembic env, helpers, versions/0001_baseline.py
```

import-linter enforces `app.main → app.api → app.modules → app.integrations → app.core` (a lower layer never imports a higher one), and keeps `core.config` / `core.ids` dependency-free. It runs in `pnpm lint:backend` and in CI. Inside a module the layering stays `router → service → (domain, repository) → models`.

## 2. Identifiers and models

| Convention | Implementation |
|---|---|
| Primary key | `UUIDPrimaryKeyMixin`: UUIDv7 generated by the application (`app.core.ids.new_id`, Python 3.14 stdlib) |
| Timestamps | `TimestampMixin`: `created_at` and `updated_at` as `timestamptz`, set by the database; `updated_at` refreshed on update |
| Optimistic locking | `VersionedMixin`: `version` column; a stale write raises `StaleDataError` → `409 CONFLICT` |
| Constraint names | `NAMING_CONVENTION` (`pk_`, `uq_`, `ix_`, `fk_`, `ck_`), deterministic for reviewable migrations |
| Relationships | Must declare `lazy="raise"` (ADR-0001); a test inspects every mapper |
| Later mixins | `TenantScopedMixin` (T01-03), campus and actor mixins with their first consumers; `SoftDeleteMixin` only when a module needs it |

## 3. Database access and transactions

- **Roles (ADR-0004):**
  - The API uses `DATABASE_URL`, the `mti_app` role: DML only, not the owner, no `BYPASSRLS`.
  - Migrations use `MIGRATIONS_DATABASE_URL` (`mti_owner`).
  - `READONLY_DATABASE_URL` (`mti_readonly`) is for reporting and the governed data agent.
  - Compose gives the owner credentials only to the one-shot `migrate` service.
- **Engine:** created in `create_app`, which opens no connection; `/health` never touches the database. Pre-ping is on; SQL and parameters are never logged by the engine. The engine is disposed on shutdown.
- **`DbSession`, one transaction per request:**
  1. The realm guard binds the trusted `RequestContext` (§6).
  2. The dependency opens a session and **one** transaction.
  3. It publishes the context with `SET LOCAL` (`set_config(..., true)`): `app.realm`, `app.request_id`, `app.tenant_id` and `app.user_id`. `app.user_id` is set only for the tenant and student realms, because platform principals are a separate identity.
  4. The handler and services run. Repositories and services never commit or roll back.
  5. On success the transaction **commits before the response is sent** (FastAPI `scope="function"`). A failed commit becomes an error response, never a false success. On any exception it rolls back.
- **No context leakage:** the settings are transaction-local; the next transaction on the same pooled connection sees none of them (tested). RLS policies read them with `nullif(current_setting('app.tenant_id', true), '')`.
- **No session without context:** `DbSession` on a route outside the realm routers raises `MissingContextError` → 500.

## 4. Migrations

- Alembic in `backend/migrations`, one linear history, revisions `0001`, `0002`, …
  - `pnpm db:migrate` upgrades the local database.
  - `pnpm db:check` fails when the models and the migrations differ.
  - In Docker, `docker compose run --rm migrate` (part of `pnpm stack:up`).
- `env.py` runs as the owner and discovers every `app/modules/*/models.py`. It takes the URL from the validated settings (or from test attributes), never from `alembic.ini`.
- `migrations.helpers.database_roles()` gives migrations the runtime role names (from the `DATABASE_URL` and `READONLY_DATABASE_URL` users), so grants and RLS never hard-code them.
- **Baseline `0001`:** no tables. It revokes write access to `alembic_version` from the runtime roles, which keep SELECT only.
- **Review checklist** (in the revision template):
  - tenant tables use `TenantScopedMixin` with an RLS policy and composite foreign keys;
  - grants are explicit;
  - the downgrade restores the previous state;
  - autogenerated output is always edited by hand.

## 5. Side effects after commit (T01-00 decision D10, as amended)

External side effects — email first (password reset, invitations; T01-04, T01-07, T01-08), later webhooks and provider calls — follow these rules:

1. **Only after a successful commit.** A side effect is registered during the request and dispatched only after the request's transaction has committed. It is never performed inside the transaction.
2. **Never after a rollback.** If the transaction rolls back (an error, a failed commit, validation), nothing is sent.
3. **After the response is sent.** Dispatch runs as a post-response task, so the response is the same whether or not an email was sent, and its timing does not reveal whether an account exists.
4. **A failed send does not undo the commit.** The committed state (for example a hashed reset token) stays valid. The failure is logged with the request ID and without the recipient's token or message body, and it is recorded as a security or audit event. The user can request again (password reset), or an administrator can resend (invitation). No automatic retry.
5. **At most once in T01.** There is no queue library yet (the queue remains undecided until the first job task). Each send has a bounded timeout. The first background-job task replaces direct dispatch with a **transactional outbox**, written in the same transaction and delivered by a worker with retries and idempotency keys: at least once, deduplicated.
6. **Secrets stay out of side-effect records.** Tokens are generated and stored hashed in the transaction; the plain token exists only in the outgoing message. Message bodies and tokens are never logged.
7. **Provider boundary.** Email goes through an `EmailSender` interface (`app/integrations/email/`) with an SMTP adapter (Mailpit locally) and a deterministic fake for tests. Tests assert: nothing is sent on rollback; sending happens after commit; a failed send leaves the committed state; and responses are identical either way.

## 6. Request context and realm routers

| Realm | Prefix (ADR-0006) | Router access in T01-01 | Becomes |
|---|---|---|---|
| Platform | `/api/v1/platform/*` | **denied** (401) | platform sessions + MFA (T01-06) |
| Tenant | `/api/v1/*` (remaining paths) | **denied** (401) | tenant sessions (T01-04), permissions (T01-05) |
| Student | `/api/v1/student/*` | **denied** (401) | student sessions (Phase 04/13) |
| Public | `/api/v1/public/*` | anonymous | tenant from a verified host (Phase 14) |
| Webhooks | `/api/v1/webhooks/*` | **denied** (401) | signature verifier per provider (Phase 09) |

- Every route is created on a router from `realm_router(realm, access=...)`.
- Its guard runs first — before validation and before any other dependency — and binds `RequestContext(realm, request_id, principal_id, tenant_id)`.
- The context is the only trusted source of realm, principal and tenant; nothing in a request body, query or header can set it.
- **Route coverage:** `tests/security/test_realm_guards.py` enumerates the application's effective routes (`fastapi.routing.iter_route_contexts`). It fails if an `/api` route has no guard, or a guard from a realm that does not own the path.

## 7. API conventions

| Topic | Rule |
|---|---|
| Success | `{"data": …, "meta": {…}}` (`Envelope`); lists `ListEnvelope` with `meta.page = {limit, offset, total}` |
| Errors | `{"error": {"code", "message", "details": [{field, code, message}], "request_id"}}` |
| Codes | `VALIDATION_ERROR` 422 · `AUTHENTICATION_REQUIRED` 401 · `PERMISSION_DENIED` 403 · `NOT_FOUND` 404 (also for other tenants' resources) · `METHOD_NOT_ALLOWED` 405 · `CONFLICT` 409 · `RATE_LIMITED` 429 · `INTERNAL_ERROR` 500 |
| Messages | Written for users; never input values, stack traces, SQL, infrastructure details or credentials |
| Requests | `RequestModel`: `extra="forbid"` (no mass assignment of `tenant_id`, status, role or version), strings stripped and bounded; fields declare tighter limits |
| Responses | `ResponseModel` (`from_attributes`) |
| Pagination (D13) | `limit` 1–100 (default 25), `offset` 0–10 000 |
| Sorting | `sort=name,-created_at` against an allow-list; at most 3 fields; rejected values are never echoed |
| Filtering | Explicit typed query parameters per endpoint; unknown values → 422 |
| Transitions | Explicit endpoints (`POST …/{id}/suspend`), never arbitrary status updates |
| Request ID | UUIDv7 per request in `X-Request-ID`, the error body and the logs; inbound `X-Request-ID` ignored |
| Headers | `/api/*` responses: `Cache-Control: no-store`, `X-Content-Type-Options: nosniff` |
| OpenAPI | Development only; `operationId = <realm>_<tag>_<function>`; error responses documented with `ErrorEnvelope` |
| Versioning | `/api/v1`; a breaking change needs `/api/v2` |

## 8. Logging

- One JSON object per line on stdout, with `timestamp`, `level`, `logger` and `message`, plus `request_id`, `realm` and `tenant_id` from the context and structured extra fields.
- Extra fields with sensitive names (password, token, secret, cookie, authorization, CSRF, session other than `*session_id`, API key, credential, OTP) are replaced by `[REDACTED]`; long values are truncated.
- One `request.completed` line per request with method, **path without query string**, status and duration (`/health` excluded).
- Uvicorn's access log is off (`--no-access-log`, and disabled in code). `httpx` and `httpcore` log at WARNING only (their INFO lines contain full URLs).
- Unexpected exceptions are logged once with their stack and request ID. The client sees only the generic 500 envelope.

## 9. Testing

| Suite | Location | Needs |
|---|---|---|
| Unit | `tests/unit` | nothing |
| API conventions | `tests/api` | nothing (probe routes on real realm routers) |
| Security | `tests/security` | nothing |
| Integration | `tests/integration` (`@pytest.mark.integration`) | PostgreSQL test database |

- Database tests use a real PostgreSQL database, never SQLite: `${POSTGRES_DB}_test`, created by `database/init/02-test-database.sh` with the same roles and grants.
- URLs come from `TEST_DATABASE_URL`, `TEST_MIGRATIONS_DATABASE_URL` and `TEST_READONLY_DATABASE_URL`.
- Without them the tests are **skipped**. With `REQUIRE_DATABASE_TESTS=1`, set in CI, the skip becomes a failure.
- In CI the backend job starts the compose `postgres` service on a fresh volume with generated, masked passwords (`scripts/ci/start-test-database.sh`).

## 11. Known limitations and follow-ups

- The API settings require `MIGRATIONS_DATABASE_URL` in staging and production (T00-04). The deployed API process should not need owner credentials. This is to be revisited with the deployment work (Phase 17); compose already withholds them from the `api` service.
- There is no readiness endpoint (database, cache) yet; `/health` is liveness only.
- The inbound `X-Request-ID` is ignored until a trusted proxy chain exists.
