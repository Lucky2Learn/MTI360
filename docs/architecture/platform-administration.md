# Platform Administration Foundation (API)

- **Status:** Decisions locked (T01-07 architecture review, 2026-10-03); implementation not started. The implementation ADR (ADR-0018) is written with the implementation.
- **Builds on:** [ADR-0004](../adr/0004-tenant-isolation.md) and [ADR-0014](../adr/0014-tenancy-core.md) (realm-agnostic tenant RLS; `system_context` refuses to run inside an HTTP request), [ADR-0013](../adr/0013-audit-events.md) (audit in the mutation's transaction), [ADR-0015](../adr/0015-identity-authentication.md) (invitations, D05), [ADR-0016](../adr/0016-authorization-rbac.md) (`authorize`, `require_permission`, `clone_system_roles`), [ADR-0017](../adr/0017-platform-identity-mfa.md) and [platform-identity.md](platform-identity.md) (platform realm, lookup and target-key transactions, D6-1 … D6-5), T01-00 decisions D10 (post-commit email), D13 (offset pagination), D15 (create, suspend and reactivate only) and D20 (API only).
- **Scope (TASKS.md T01-07):** tenant provisioning (tenant, primary campus, cloned system roles, owner invitation); tenant list and detail; suspend and reactivate; platform users (list, create by invitation, update, suspend, reactivate, MFA-reset route); platform audit read. Screens belong to Phase 02. Deactivation, cancellation, subscriptions, entitlements, domains, support sessions and the other wizard steps (PLAT-06) are out of scope.
- **Resolves:** [INC-39](spec-inconsistencies.md#inc-39--platform-provisioning-cannot-write-tenant-owned-rows) (design; closed by the implementation ADR). **Leaves open:** [INC-38](spec-inconsistencies.md#inc-38--unscoped-has-no-consumer).

## Locked decisions

| # | Decision |
|---|---|
| **D7-1** (O1) | **Provisioning write path.** A named provisioning transaction, owned by the tenant provisioning service alone, creates a tenant in one transaction. It is built on `context_transaction` with the authorized platform principal and, as the trusted tenant, **only the new tenant's server-generated ID** (never request input). Inside it the existing realm-agnostic tenant RLS admits the tenant's own rows, so no tenant-owned policy is widened. It creates the tenant, the primary campus, the cloned system roles (`clone_system_roles`), the owner's membership with `INSTITUTE_OWNER` and the owner invitation. The only new policy is a narrow `users` insert keyed on a provisioning setting published by the same module, because `users` inserts are system-only today. `system_context` is not used (it refuses to run inside an HTTP request). A static test allows only the provisioning module to publish the provisioning setting or build a platform context with a tenant. The tenant is created and the event `platform.tenant.created` is audited in the same transaction. |
| **D7-2** (O2) | **Platform user administration RLS.** A target-key transaction, the pattern of the T01-06 MFA-reset transaction. The service runs `authorize()` (permission and step-up) first, then opens a transaction with the authorized principal and **one** target platform-user ID. Policies on `platform_users` (update), `platform_user_roles` (insert and delete) and `platform_sessions` (revoke) admit only that target. A new user's ID is server-generated and published the same way for the insert. The T01-06 own-row-only rules for ordinary platform access are unchanged. A static test allows only the administration module to publish the key. |
| **D7-3** (O3) | **Platform user onboarding.** A dedicated `platform_user_invitations` table: a single-use, expiring token stored only as an HMAC, sent in the link fragment (never a path or query string), never logged and never returned by the API. The user is created as `INVITED` with roles and no credential. A public preview and accept pair under `/api/v1/platform/auth/invitations/*` returns one generic `404` for unknown, expired, used and revoked tokens. Acceptance sets the password (T01-04 password rules) and activates the user. The first sign-in then requires MFA enrolment (D6-1, D6-4). No temporary passwords, and tenant invitations are not reused. Email is sent after commit (D10). Creation, resend, acceptance and revocation are audited. Expiry is evaluated when the token is used; there is no expiry job. |
| **D7-4** (O7) | **Platform user suspend and reactivate need step-up.** `platform_user.suspend` and `platform_user.reactivate` are declared `requires_step_up`. **This extends the locked D6-5 list** (`tenant.suspend`, `tenant.reactivate`, `platform_user.create`, `platform_user.update`). The window (10 minutes), the error (`403 STEP_UP_REQUIRED`) and enforcement in `authorize()` are unchanged. The flag lives in code only, so the permission catalogue does not change. Both actions require a reason (1–500 characters, in audit metadata) and the current `version`. Suspension revokes the user's platform sessions in the same transaction. Reactivation restores `ACTIVE` only: the user's MFA factor stays and sign-in still requires MFA. |
| **D7-5** (O7) | **Self-protection.** An administrator cannot suspend, demote or reset the MFA of their own account. The last active `SUPER_ADMIN` cannot be suspended or lose the role. The check runs under a row lock on the active `SUPER_ADMIN` rows, so two concurrent changes cannot both pass. The bootstrap CLI remains the break-glass path (D6-1). |
| **D7-6** (O8) | **Tenant suspension revokes live tenant sessions.** In the transaction that sets `SUSPENDED`, every unrevoked `user_sessions` row whose `active_tenant_id` is that tenant is revoked with a new reason, `tenant_suspended` (a CHECK constraint change in migration `0007`). Only those rows are reachable: a narrow `user_sessions` update policy is keyed on a target-tenant setting published by the suspension service, not on `app.tenant_id`. Sessions in another institute or without an active institute are unaffected; the T01-03 status check still blocks any later switch into the tenant. Reactivation never restores revoked sessions. The suspension and the number of revoked sessions are audited (`platform.tenant.suspended`). |

## Defaults recorded (non-blocking)

| # | Default |
|---|---|
| **D7-7** (O4) | **Owner email with an existing tenant account.** The membership and an "existing account" invitation are created; the identity and its credential are never changed (T01-04 D05). A `DISABLED` identity is refused with `409 CONFLICT`. Platform administrators may learn that the identity exists; nothing reaches the tenant realm. |
| **D7-8** (O5) | **Owner invitation resend.** In scope: `POST /api/v1/platform/tenants/{id}/owner-invitation/resend` under `tenant.create` without step-up, only while the owner's membership is `INVITED`. It revokes the open invitation and issues a new one (7 days). Because it targets an existing tenant, it does not use the D7-1 transaction. It uses a key matched to that membership's invitations only. Audited; email after commit. |
| **D7-9** (O6) | **Platform audit read.** `GET /api/v1/platform/audit-events` under `audit.read`. Filters: category, event type, tenant (the `tenant_id` column or a tenant target), actor (`principal_id`), target type and ID, and a created-at range. Offset pagination (D13), newest first. The response gives the stored audit fields (`id`, `created_at`, `realm`, `category`, `event_type`, `principal_id`, `tenant_id`, target, `request_id`, metadata); metadata is already redacted at write time (INC-35 stays as recorded). Reading is not itself audited in T01. A `(principal_id, created_at)` index is added only if the actor filter needs it. |
| **D7-10** (O9) | **No `unscoped()`.** T01-07 adds no general tenant-data escape hatch; INC-38 stays open for support sessions (T02-04). |

## Architecture constraints

- **Order of checks.** Every route is in the platform realm on an MFA-verified session, with `require_permission`. Each service calls `authorize()` **before** it opens a target-key or provisioning transaction. A tenant or platform-user ID in a path is a target only and never becomes the request's trusted context.
- **No new general bypass.** Each new key is published by one module, matched by equality, and opens one operation on one target. A static test lists the modules allowed to publish them, like the T01-06 lookup-key test.
- **Concurrency.** Tenant and platform-user mutations take the current `version` (`409 CONFLICT` when stale). Tenant transitions use the D15 rules in `tenants/domain.py`.
- **Audit.** Mutations are audited in their transaction (D22). Platform events about an existing tenant carry it as the target. Provisioning events carry the new tenant as `tenant_id`, because they are written in the provisioning transaction. **Consequence for T01-08:** the tenant audit read policy shows a tenant's rows whatever realm wrote them, so T01-08 decides whether tenant administrators see platform-written events. No email, token, password or reason text beyond the stated reason field appears in metadata.
- **Migration `0007`** carries the new table, the narrow policies, the `tenant_suspended` revoke reason and any audit index. It follows the `0004`–`0006` conventions: frozen copies, a downgrade without leftovers, and RLS and grant tests.
- **Tests.** Tenant A cannot reach tenant B through any new route or key. The static key tests. Step-up, self-protection and last-`SUPER_ADMIN` races. Session revocation on suspension. Invitation token generic responses and single use. Route coverage for every new route.
